# خارطة تطوير SAS PRO QUANT

## المبدأ الحاكم: لا تعطيل ولا كسر

يُطوّر SAS PRO QUANT كطبقة إضافية على المشروع الحالي. لا يُسمح بإعادة بناء الموقع أو استبدال Telegram أو تغيير القناة أو الاشتراكات من أجل إضافة المحرك الكمي.

### مناطق محمية
- `web/` وواجهات الموقع وMini App: لا تغيير بصري أو وظيفي ضمن المرحلة الكمية إلا عبر طلب منفصل واختبارات عقد API.
- `app/main.py`: لا تغيير لمسارات الموقع الحالية أو المصادقة أو الاشتراكات. أي API كمية جديدة تكون إضافية وبصلاحيات واضحة.
- `app/telegram.py` وعمليات الإرسال في `app/jobs.py`: لا تغيير لتنسيق القناة أو شروط النشر الحالية إلا بعد اختبار منفصل.
- `app/subscriptions.py` و`app/admin.py`: لا تغيير للتجربة أو الدفع أو صلاحيات الأعضاء.
- قاعدة البيانات: تغييرات additive فقط، مع migration متوافق، ولا حذف أو إعادة ضبط لأي سجل قائم.

## النطاق الأول

- السوق: الأسهم الأمريكية.
- نطاق السعر: 0.30 إلى 6.00 دولار وفق سعر موثق وحديث.
- رأس مال المحفظة الافتراضية الابتدائي: 10,000 دولار، قابل للتغيير من الإعدادات.
- التنفيذ: محاكاة افتراضية فقط؛ لا أوامر حقيقية ولا ربط وسيط في هذه المرحلة.
- دورة القياس: 60 جلسة تداولية كفترة تقييم أولية، لا كضمان للنتائج أو كدليل كافٍ وحده على صلاحية استراتيجية.

## المحركات

### 1. الاكتشاف وجودة البيانات
- إعادة استخدام تسلسل مزودي البيانات الحالي.
- احترام `app/twelve_guard.py`؛ Twelve Data احتياطي اختياري فقط ولا طلب مباشر يتجاوز الحماية.
- عدم إضافة Yahoo Finance للرادار.
- حفظ المصدر والطابع الزمني والسعر والحجم وسبب الرفض.
- رفض البيانات المفقودة أو القديمة أو المتعارضة، وعدم ملء الحقول بالتخمين.

### 2. التقييم الكمي
- إعادة استخدام `app/quality_score.py` كبداية، لا استبداله دون مقارنة.
- توحيد عوامل الاتجاه والزخم وRVOL والاختراق والسيولة وتأكيد الحركة وجودة البيانات وحالة السوق.
- عدم اعتبار غياب الدليل درجة إيجابية.
- حفظ إصدار النموذج والأوزان والدرجات الفرعية عند صدور الإشارة.
- الدرجة مقياس ترتيب وليست احتمال نجاح أو توصية.

### 3. بوابات المخاطر
- بوابات لا يمكن تجاوزها بالنقاط: حداثة السعر، سلامة البيانات، السيولة، قابلية حساب الوقف، نسبة العائد للمخاطرة، حالة التداول، وحدود التعرض.
- حساب حجم المركز من ميزانية المخاطرة والحد الاسمي للتعرض.
- منع إضافة مركز عند عدم وجود وقف موثق أو عند فشل جودة البيانات.
- تقليل المخاطرة أو منع فتح صفقات جديدة عند ارتفاع مخاطر السوق.
- لا أهداف أو أوقاف أو أسعار دخول مختلقة.

### 4. المحفظة الافتراضية
- تسجيل كل إشارة وقرار قبول/رفض ووقت الرصد.
- لا يفترض أن سعر الإشارة هو سعر تنفيذ مضمون.
- محاكاة التعبئة تراعي فجوات الأسعار، والسبريد والانزلاق والعمولات وفق افتراضات معلنة.
- عند غياب بيانات OHLC أو تفاصيل كافية، توسم نتيجة التنفيذ بأنها غير محسومة بدلاً من اختراع تعبئة.
- معالجة لمس الوقف والهدف في الشمعة نفسها بطريقة محافظة، مع أولوية الوقف إذا تعذر معرفة مسار السعر داخل الشمعة.
- تسجيل تعدد الأهداف، الإغلاق الجزئي، الوقف المتحرك، والإلغاء كأحداث مستقلة قابلة للتدقيق.

### 5. الأداء
- Win rate وProfit Factor وExpectancy وAverage P&L وMax Drawdown والعائد التراكمي.
- فصل الصفقات المفتوحة عن الصفقات المغلقة.
- احتساب الرسوم والانزلاق عند توفر نموذج معلن.
- عرض عدد العينات والفترة ومصدر الأسعار وطريقة المحاكاة بجانب كل مقياس.
- عدم عرض نسبة نجاح أو Sharpe أو Profit Factor على أنها موثوقة عند غياب بيانات كافية؛ تظهر غير متاحة عند عدم انطباقها.

### 6. التعلم المنضبط
- استخدام النتائج المكتملة فقط.
- مقارنة الاستراتيجية الحالية بنسخة مرشحة على بيانات منفصلة زمنياً (out-of-sample) مع منع تسرب البيانات المستقبلية.
- لا تعديل تلقائي مباشر على قواعد الإنتاج.
- أي تغيير يُسجل بإصدار، ويختبر تاريخياً ثم في forward paper mode، ويحتاج اعتماداً قبل التفعيل.
- الاحتفاظ بإمكانية الرجوع إلى الإصدار السابق.

## مراحل التنفيذ ومعايير القبول

### المرحلة 0 — الحماية والتدقيق
- توثيق عقود API الحالية والصفحات والوظائف المحمية.
- خط أساس لاختبارات الموقع وTelegram والاشتراكات والرادار.
- نسخ احتياطي وخطة رجوع قبل أي migration أو نشر.
- القبول: لا تغييرات تشغيلية على الإنتاج.

### المرحلة 1 — محرك حسابي معزول
- حساب حجم المركز.
- محاكاة محافظة للوقف والهدف.
- حساب مؤشرات الأداء من صفقات مغلقة فقط.
- القبول: اختبارات وحدات ناجحة ولا اعتماد على واجهة أو شبكة أو قاعدة البيانات.

### المرحلة 2 — نموذج بيانات إضافي
- جداول مستقلة للمحفظة والحساب الافتراضي والمراكز والأحداث والتنفيذات.
- migrations additive وidempotent.
- مفاتيح فريدة تمنع التكرار.
- القبول: اختبار الترحيل على قاعدة مؤقتة ونجاح قراءة البيانات القديمة دون تعديل.

### المرحلة 3 — ربط الإشارات
- التقاط الإشارات الجديدة المؤهلة فقط.
- حفظ لقطة البيانات ودرجة الجودة وإصدار النموذج.
- لا تغيير لقواعد النشر الحالية.
- القبول: عدم تكرار الإشارات وعدم تغيير عدد/محتوى رسائل القناة القائمة.

### المرحلة 4 — محاكاة ومتابعة الصفقات
- تحديث الصفقات من بيانات السوق الموثوقة وفق جدولة محسوبة.
- لا استهلاك غير ضروري لحصص API.
- توثيق أسباب عدم التنفيذ أو الإغلاق.
- القبول: اختبارات حالات فجوة السعر وتزامن الوقف/الهدف والأسعار المفقودة.

### المرحلة 5 — API ولوحة التحليلات
- endpoints جديدة للوحة الكمية، دون كسر endpoints الحالية.
- صلاحيات تحقق خادمية؛ لا ثقة في إخفاء الواجهة وحده.
- القبول: اختبارات عقد API ومقارنة snapshots للمسارات الحالية.

### المرحلة 6 — التعلم والتقييم
- تقارير أسبوعية ونسخ استراتيجيات ومقارنة خارج العينة.
- لا تعديل تلقائي للإنتاج.
- القبول: إعادة إنتاج المقاييس من سجل الصفقات الخام.

### المرحلة 7 — تشغيل تجريبي
- 60 جلسة تداولية من المحاكاة الورقية بعد اكتمال التكامل.
- تقارير يومية وأسبوعية، ومراجعة جودة البيانات والنتائج.
- لا انتقال إلى أموال حقيقية دون قرار مستقل ومراجعة تنظيمية ومخاطر.

## بوابات الإصدار الإلزامية

1. `python -m compileall -q app`
2. `python -m unittest discover -s tests -p "test*.py" -v`
3. اختبارات حدود المعمارية.
4. اختبارات API للموقع وMini App والمصادقة والاشتراكات.
5. اختبارات Telegram formatting / duplicate delivery / channel gate.
6. فحص diff بحثاً عن أسرار أو تغييرات غير مقصودة.
7. مراجعة migrations وخطة الرجوع.
8. نشر عبر GitHub Actions فقط بعد نجاح كل البوابات.
9. فحص صحة الإنتاج بعد النشر، والتراجع إذا فشل أي فحص.

## تعريف النجاح

يكون SAS PRO QUANT جاهزاً للتجربة عندما يكتشف ويقيّم ويرفض ويختار بأسباب قابلة للتدقيق، ويسجل محاكاة تنفيذ واقعية، ويحسب الأداء من بيانات تاريخية قابلة لإعادة الإنتاج، مع بقاء الموقع وMini App وTelegram والقناة والاشتراكات مستقرة كما كانت.
